# RFC: Channels in Signal Groups

*A feature proposal for the Signal community and Signal engineering. Companion to code-level
analysis; no code is proposed here until the design and protocol allocations are agreed.*

## 1. Motivation

Large Signal groups mix everything into one stream: planning, logistics, off-topic chatter.
Members' only defense is muting the entire group, which throws away the messages they *do*
care about. Other group messengers (GroupMe topics, Discord/Slack channels) solve this by
letting one group host multiple named message streams. This RFC proposes channels for Signal
groups with three properties Signal users would expect:

1. **No new metadata.** Channel names are end-to-end encrypted like the group title; channel
   assignment of a message travels inside sealed-sender content. Servers learn nothing new
   beyond what encrypted group state already reveals (an entry count, like member count).
2. **No new cryptography.** Everything reuses existing mechanisms: zkgroup attribute-blob
   encryption, GroupsV2 change actions, Storage Service records.
3. **Graceful mixed-version behavior.** Groups containing old clients keep working, by
   construction of the existing `changeEpoch` machinery plus a deliberate rendering choice
   (§6).

## 2. Goals and non-goals

**Goals**
- Group admins can create, rename, and delete channels within a group.
- Every group has a default channel (#general); existing groups and old messages need no
  migration.
- Members can mute individual channels; @mentions override a channel mute the same way they
  override a group mute today. The existing whole-group mute is unchanged and silences
  everything.
- Per-channel mutes sync across a user's devices and survive backup/restore.
- Pinned messages are channel-scoped: each channel shows its own pins. Who may pin is
  unchanged from groups today (pinning follows the group's "edit group info" access
  control, so any member may pin in a default-settings group). This costs no protocol
  change; see §4.

**Non-goals (v1)**
- Membership-restricted or hidden channels. All members see all channels. (Restricting
  visibility would break the one-sender-key/one-blob-key-per-group model; deliberately out.)
- Per-channel posting or pinning permissions (announcement-style channels), renaming
  #general, channel reordering, per-channel drafts/typing/read-position, channel-scoped
  search.

## 3. Group state: channel definitions

Channels are group state, stored encrypted on the groups server and modified through
GroupsV2 change actions like every other group attribute.

```proto
// Groups.proto (field numbers illustrative; to be allocated upstream)
message Channel {
  bytes id    = 1;   // 16 random bytes, generated by the creating client
  bytes title = 2;   // encrypted GroupAttributeBlob (new channelTitle arm), like title/description
}

message Group {
  // ...
  repeated Channel channels = 15;
}

message GroupChange.Actions {
  message AddChannelAction         { Channel channel = 1; }
  message ModifyChannelTitleAction { bytes id = 1; bytes title = 2; }
  message DeleteChannelAction      { bytes id = 1; }
  repeated AddChannelAction         addChannels         = 29;  // new changeEpoch (next available)
  repeated ModifyChannelTitleAction modifyChannelTitles = 30;
  repeated DeleteChannelAction      deleteChannels      = 31;
}
```

Server-side validation (groups server):
- All three actions require the **ADMINISTRATOR** role. (A dedicated
  `AccessControl.channels` knob is a natural extension if preferred; see §9.)
- Limits: at most **32** channels per group; title ciphertext 1–512 bytes; unique ids;
  channel actions rejected at group creation in v1.
- The actions are assigned the next available `changeEpoch`. Existing epoch machinery does
  the rest: clients advertising an older max epoch receive full snapshots instead of
  unparseable actions, and render a generic "group was updated" event.

**The default channel is implicit.** #general is "the absence of a channel id": it has no
entry in group state, cannot be deleted, and every message ever sent before this feature is
automatically a #general message. This is what makes the feature migration-free.

**Deleting a channel folds its messages into #general.** Clients treat a channel id that is
not in current group state as #general at display time. No message rewriting, no tombstones.

## 4. Message tagging

```proto
// SignalService.proto (field number illustrative)
message DataMessage {
  // ...
  optional bytes channelId = 30;   // absent = #general
}
```

The field lives inside sealed-sender content: no server sees or routes on it. Receiving
clients route by these rules:

- `channelId` absent routes to #general.
- `channelId` present but unknown (deleted channel, or a create/post race) routes to #general.
  Routing, never dropping: a message must never disappear because of channel state skew.
- **Quote-following:** a message with no `channelId` that quotes a message in channel C is
  displayed in channel C. This is the mitigation for old clients replying to channel
  messages (§6).

Group-state ordering is already guaranteed: clients hold messages referencing a newer group
revision until they have fetched that revision, so a channel exists locally before the first
message tagged with it is processed.

Channel scoping extends to every message-anchored feature at no protocol cost. Pins,
reactions, replies, and receipts all reference a target message, and every message carries
its channel, so a channel's pin bar is simply the group's pin list filtered by each pinned
message's channel. A pin made from an old client's flattened view still lands in the right
channel, because the target message knows where it lives. Pins in a deleted channel follow
their messages into #general. The pin cap, per conversation today, becomes per-channel
client policy.

## 5. Muting

Three-level precedence, top wins:

1. **Global group mute** (existing `mutedUntilTimestamp`): unchanged; silences the whole
   group including all channels.
2. **Per-channel mute**: new; silences one channel.
3. **Mention override**: an @mention notifies through a channel mute, subject to the
   existing "don't notify for mentions if muted" setting, exactly mirroring today's group-mute
   behavior.

Muted channels are excluded from the conversation's unread badge (the GroupMe/Slack
convention); unmuted channels count normally.

**Multi-device sync** rides the existing Storage Service group record, which is opaque
ciphertext to the storage server:

```proto
// StorageService.proto (field number illustrative)
message ChannelMute {
  bytes  channelId           = 1;
  uint64 mutedUntilTimestamp = 2;   // same clamp semantics as the group-level field
}
message GroupV2Record {
  // ... mutedUntilTimestamp = 6 stays as the global mute ...
  repeated ChannelMute channelMutes = 13;
}
```

**Backups**: the backup format mirrors group state (`GroupSnapshot` gains `channels`), chat
items gain an optional `channelId`, and per-channel mutes sit beside the existing per-chat
`muteUntilMs`. Backup validators treat unknown fields as warnings, so older validators remain
compatible.

## 6. Mixed-version behavior (the key compatibility decision)

Old clients ignore the unknown `DataMessage.channelId` field and render channel messages
**flattened** into the single group timeline. We propose *not* bumping
`requiredProtocolVersion`: the alternative replaces every channel message with an "update
Signal to view" placeholder, which is strictly worse for a stream users are meant to be able
to mute, and there is no middle ground between the two.

Consequences and mitigations:
- Old clients see one merged timeline; the group remains fully readable and functional.
- Replies sent from old clients carry no channel id; quote-following (§4) routes them into
  the right channel on updated clients. Non-reply messages from old clients land in #general.
- Channel create/rename/delete appear to old clients as generic group-update events via the
  epoch snapshot fallback.

## 7. Client UX sketch

- A channel switcher in the group conversation view (chips or a header dropdown); #general
  first, then channels in group-state order, with per-channel unread badges and a strongly
  distinct active-chip state. A prototype showed the feature reads as inert without both.
- Each message carries a compact #channel label in its metadata row, so attribution
  survives outside the filtered view (quote-followed replies, the #general fold, and
  recordings or screenshots).
- Read state is channel-scoped: entering a channel lands on its first unread message, and
  only messages actually brought into view are marked read, so reading two of ten leaves
  eight unread. Prototyping showed this costs little because seen/read state is already
  per-message on every platform.
- A "Channels" section in group settings, visible to all, editable by admins.
- Long-press or right-click on a channel opens mute options mirroring today's mute durations.
- The pinned-message bar shows the active channel's pins.
- Timeline storage is one column on the message table plus a query predicate, the same
  pattern all three clients already use to segregate story replies from the main timeline.

## 8. Privacy summary

- Channel titles: encrypted with the group's existing attribute blob key; server sees
  ciphertext only.
- Channel membership of a message: inside sealed-sender content; invisible to all servers.
- Per-channel mutes: inside encrypted Storage Service records; invisible to the storage
  server.
- What servers *can* newly observe: the groups server sees that a group's encrypted state
  contains N channel entries and that channel-type actions occur (it must, to validate
  admin-only access), the same class of visibility it already has for members, pending
  members, and banned lists. The chat server observes nothing new. Push notifications are
  unchanged (content-free wake-ups; all muting is client-side).

## 9. Rollout and open questions for Signal

Proposed staging, following the pattern of recent group features: groups server first, then
backup format, then client receive-side shipped dark for at least one release, then send-side
and UI behind a remote flag.

Questions we'd want Signal's guidance on before writing code:
1. `changeEpoch` and proto field number allocation (all numbers above are placeholders;
   these are upstream-managed and moving).
2. Admin-only hardcoded vs. an `AccessControl.channels` knob in v1.
3. Confirmation of the implicit-#general design (vs. an explicit default-channel entry,
   which would allow renaming #general at the cost of migration complexity).
4. Badge policy confirmation: muted channels excluded from the conversation badge.
5. Placement of per-channel mute in the backup format (proposed: beside the per-chat mute).
6. Channel cap, title-size limit, and per-channel pin cap values (32 channels / 512-byte
   ciphertext proposed; production values are operator configuration).
